# ADR-0010: Manifest write conflicts are resolved with ETags and a typed conflict policy

- **Status:** Accepted
- **Date:** 2026-09-02

## Context
A manifest lives in SharePoint, where other people and other processes can change it between
the moment this app reads it and the moment it writes. Silently overwriting someone's file is
data loss.

## Decision
Manifest writing is conditional and policy-driven.

1. Read the existing manifest and capture its `eTag`.
2. Choose behaviour by `ManifestConflictPolicy`: `Replace`, `UpdateSafely`, `CreateTimestampedVersion`,
   `Skip`, or `Fail`.
3. Write with `If-Match: <eTag>`. A `412 Precondition Failed` means the remote copy changed;
   the write is **not** retried blindly — it surfaces as a typed `ManifestConflict` outcome.

**Defaults:** `UpdateSafely` when the existing file was generated by this application and
parses cleanly; otherwise `CreateTimestampedVersion`. A file this application did not write is
never overwritten by default.

## Consequences
- A remotely modified manifest cannot be clobbered without an explicit `Replace` choice.
- Foreign files at the manifest path are preserved.
- Requires the plain-text format to be machine-parseable and self-identifying, which is why it
  carries `Schema Version` and per-entry `Drive ID` / `Item ID` (see ADR-0007).
- Generated manifest names are excluded from discovery by default so a job never ingests its
  own output.

## Alternatives considered
- **Always overwrite** — simple and destructive.
- **Always timestamp** — safe but litters libraries with near-duplicate files.
